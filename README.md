# RAG-система анализа транскриптов интервью

RAG-система для поиска и анализа транскриптов интервью: чанкинг, эмбеддинги
(BAAI/bge-m3), персистентная векторная база (ChromaDB), генерация ответов
через LLM (RouterAI). База хранится в папке `chroma_db/` и не пересоздаётся
заново при каждом запуске.

## Структура проекта

```
rag-transcripts/
├── data/
│   ├── docx/               ← сюда положи исходные .docx-транскрипты
│   ├── audio/               ← сюда — аудио/видео, если понадобится Whisper
│   └── transcripts/         ← сюда попадут JSON после парсинга/распознавания
├── chroma_db/                ← персистентная база (создастся сама)
├── n8n_workflows/             ← воркфлоу для Telegram-бота и автообработки
├── config.py                  ← пути, ключи, константы
├── parse_docx.py              ← парсинг .docx в JSON
├── transcribe.py              ← (опционально) распознавание аудио через Whisper
├── summarize.py                ← суммаризация транскриптов через RouterAI
├── indexing.py                  ← чанкинг + эмбеддинги + запись в ChromaDB
├── rag.py                        ← линейный RAG-запрос к базе знаний
├── graph_rag.py                   ← self-correcting RAG на LangGraph (см. ниже)
├── mcp_server.py                   ← MCP-сервер, инструмент search_transcripts (см. ниже)
├── app.py                           ← Streamlit-интерфейс
├── api.py                            ← FastAPI HTTP API (для n8n и внешних систем)
├── qdrant_indexing.py                 ← перенос эмбеддингов в Qdrant (см. ниже)
├── compare_recall.py                   ← сравнение ChromaDB vs Qdrant
├── compare_answers.py                   ← сравнение rag.py vs graph_rag.py
├── requirements.txt
└── .env.example

Только локально, не публикуются (eval-датасет содержит чувствительные
данные клиента):
├── eval_embeddings.py    ← сравнение моделей эмбеддингов
└── inspect_chroma.py      ← просмотр структуры базы
```

## Установка

```
pip install -r requirements.txt
```

Скопируй `.env.example` в `.env` и впиши свой RouterAI-ключ:

```
copy .env.example .env
```

### Дополнительные зависимости (по необходимости)

Эти пакеты нужны только для отдельных разделов ниже, не для базового
запуска `rag.py`/`app.py` — не ставь без необходимости:

- Сравнение с Qdrant: `pip install qdrant-client`
- LangGraph self-correcting RAG: `pip install langgraph`
- MCP-сервер: `pip install mcp`
- Распознавание аудио (Whisper): `faster-whisper` и `torch`
  (закомментированы в requirements.txt — тяжёлые библиотеки)

## Порядок запуска

1. Положи `.docx`-файлы транскриптов в `data/docx/`
2. Спарси их в JSON:
   ```
   python parse_docx.py
   ```
3. (Опционально) Сделай краткие summary через LLM:
   ```
   python summarize.py
   ```
4. Построй/обнови векторный индекс:
   ```
   python indexing.py
   ```
5. Задай вопрос к базе знаний:
   ```
   python rag.py
   ```

Если появятся новые аудио/видеозаписи для распознавания — поставь
дополнительно `faster-whisper` и `torch` (см. раздел выше) и запусти:
```
python transcribe.py путь/к/файлу.mp4
```

## Streamlit-интерфейс

Загрузка .docx-файлов прямо в браузере, суммаризация и вопросы к базе знаний
без командной строки. Запускается локально, без Colab/ngrok/туннелей —
просто открывается на `localhost:8501`.

```
streamlit run app.py
```

Ключ RouterAI подхватится из `.env` автоматически; если файла нет — можно
ввести его прямо в поле в левой панели интерфейса.

## HTTP API (для n8n и других внешних систем)

```
uvicorn api:app --reload --port 8000
```

- `GET /health` — проверка, что сервис жив, и сколько чанков в базе
- `POST /query` — вопрос к базе знаний: `{"question": "...", "top_k": 5}`,
  в ответ `{"answer": "...", "chunks_in_base": N}`
- `POST /process/parse` — парсит новые `.docx` из `data/docx/` в JSON
  (пропускает уже распарсенные), в ответ `{"found": N, "parsed": N, "skipped": N}`
- `POST /process/summarize` — суммаризация новых транскриптов через RouterAI,
  в ответ `{"found": N, "processed": N, "skipped": N, "failed": N}`
- `POST /process/index` — индексация новых транскриптов в ChromaDB,
  в ответ `{"new_files": N, "skipped_files": N, "total_chunks": N}`
- `POST /upload-transcript` — принимает `.docx` (multipart, поле `file`) и
  сохраняет в `data/docx/`, откуда его подхватит `/process/parse`
- `http://localhost:8000/docs` — интерактивная документация (Swagger UI)

## Оценка и выбор модели эмбеддингов

Изначальный выбор модели (`paraphrase-multilingual-mpnet-base-v2`) был
сделан без сравнения — она оптимизирована под задачу paraphrase/semantic
similarity, а не под retrieval, что и подтвердилось на практике.

Сравнил три модели на eval-датасете из 7 реальных вопросов к базе,
recall@5 на уровне документа (`eval_embeddings.py`):

| Модель                                   | recall@5 |
|-------------------------------------------|----------|
| paraphrase-multilingual-mpnet-base-v2 (была) | 57.14%   |
| intfloat/multilingual-e5-large             | 85.71%   |
| **BAAI/bge-m3 (выбрана)**                  | **100.00%** |

**Ограничение теста:** выборка небольшая (7 вопросов), и для части
multi-hop вопросов (требующих синтеза из нескольких интервью) критерий
"правильного" источника был широким — засчитывался успех, если совпал
хотя бы один из 20-30 приемлемых файлов. Это могло завысить итоговые
цифры относительно более строгого теста. Разница между моделями
(57% → 85-100%) слишком велика, чтобы быть только методологическим
шумом, но точные абсолютные значения стоит уточнять на более строгом
и большем датасете.

Выбрана `BAAI/bge-m3` — специализирована под retrieval, дополнительно
поддерживает длинные тексты и мультиязычность. `intfloat/multilingual-e5-large`
показала на этом тесте второе место, но требует специального префикса
(`query: ` / `passage: `) к тексту при энкодинге — без него качество
на бенчмарках заметно проседает.

## Telegram-бот и автообработка через n8n

Готовые к импорту воркфлоу лежат в `n8n_workflows/`:

- **`telegram_bot.json`** — бот отвечает на вопросы к базе знаний и принимает
  новые транскрипты прямо в чате. Работает через long polling
  (`getUpdates`) — n8n сам опрашивает Telegram каждые 10 секунд, входящий
  вебхук/туннель не нужен вообще (важно, так как ngrok/Cloudflare Tunnel не
  работают стабильно из РФ).
- **`process_transcripts.json`** — переиспользуемая цепочка
  парсинг → суммаризация → индексация, вызывается как сабворкфлоу.
- **`auto_process_schedule.json`** — раз в 15 минут проверяет `data/docx/`
  через `process_transcripts` и, если появились новые файлы, шлёт
  уведомление в Telegram.

### Как поднять

1. `docker start n8n`, открыть `http://localhost:5678`.
2. Импортировать все три файла (Workflows → Import from File) —
   **сначала `process_transcripts.json`**, он используется двумя другими.
3. В `telegram_bot.json` и `auto_process_schedule.json`:
   - в узле **Config** вписать `telegram_token` (получен через @BotFather)
     и `allowed_chat_ids`/`allowed_chat_id` — свой Telegram `chat_id`
     (узнать: написать боту и один раз вручную открыть
     `https://api.telegram.org/bot<TOKEN>/getUpdates`, или спросить у
     `@userinfobot`). Без allow-list бот отвечал бы любому, кто его найдёт, —
     каждый ответ это платный вызов Claude через RouterAI.
   - в узле **Execute Workflow** выбрать из списка `Process Transcripts`
     (привязка по ID не переносится между инстансами n8n при импорте).
4. Активировать оба воркфлоу.

Написав боту текстовый вопрос, получишь ответ на основе транскриптов из базы;
отправив `.docx`, он сохранится в `data/docx/` и сразу проиндексируется.

## Оценка и выбор векторной БД

Проведено сравнение ChromaDB (текущая база) и Qdrant, чтобы понять,
стоит ли переходить на более "промышленную" векторную БД по мере роста
проекта.

**Методология:** тот же eval-датасет, что использовался при выборе модели
эмбеддингов (7 вопросов с expected_sources). Данные в Qdrant загружены
параллельно, без пересчёта эмбеддингов (`qdrant_indexing.py`) — чтобы
сравнение баз было честным при идентичных векторах.

**Результат:**

| Метрика                  | ChromaDB | Qdrant (gRPC) |
|---------------------------|----------|---------------|
| hit_rate@5                | 100%     | 100%          |
| Средняя латентность       | 5.4 ms   | 6.4 ms        |

**Честная оговорка:** на текущем масштабе (2241 вектор, 53+ транскрипта)
разница между базами в пределах погрешности — обе справляются мгновенно.
При запросах через HTTP Qdrant показывал заметно более высокую латентность
(16.5 ms против 10.4 ms), но это оказалось транспортным overhead, а не
свойством поискового движка — через gRPC разница почти исчезла.

**Решение:** остаться на ChromaDB для текущего масштаба проекта. Миграция
на Qdrant задокументирована и воспроизводима (`qdrant_indexing.py`,
`compare_recall.py`) — имеет смысл при росте объёма данных на порядки или
при необходимости операционных возможностей, которых нет в Chroma из коробки
(фильтрация по метаданным на масштабе, бэкапы, апдейт без даунтайма).

## LangGraph: self-correcting RAG (параллельная версия)

Помимо линейного `rag.py`, реализована graph-версия того же RAG на LangGraph
(`graph_rag.py`): после поиска отдельный узел (`grade`) оценивает, отвечает ли
найденный контекст на вопрос, и при необходимости переформулирует запрос
(`rewrite`) и повторяет поиск — с ограничением на число попыток. Повторные
попытки исключают уже найденные чанки и накапливают контекст.

**Первая версия графа дополнительно включала узел-роутер**, решавший, нужен
ли поиск вообще. При сравнении на eval-датасете роутер один раз ошибочно
классифицировал предметный вопрос как не требующий поиска — риск оказался
неоправданным на этом масштабе, узел убран.

**Результат на eval-датасете (7 вопросов):** обе версии упоминают ожидаемый
источник в 7/7 ответах. Цикл самопроверки в отдельных случаях даёт более
полный ответ там, где линейная версия честно признаёт нехватку контекста.

**Точная стоимость:** линейная версия — 22 230 токенов суммарно на 7 вопросов
(1 вызов LLM на вопрос). Графовая — 91 579 токенов (в среднем 4.3 вызова на
вопрос) — **в 4.1 раза дороже**, что почти в точности совпадает с ростом по
числу вызовов LLM (×4.3). Оговорка: RouterAI возвращает два независимых
представления usage (`prompt/completion_tokens` и `input/output_tokens`),
которые не совпадают между собой на 15-20% — вероятно, разные способы
подсчёта на стороне прокси; для сравнения использован `total_tokens` как
более стандартное поле.

**Решение:** в прод не переводится — на текущем масштабе линейная версия
даёт тот же формальный результат за четверть стоимости. Граф ценен для
более сложных вопросов, где линейная версия чаще сдаётся — задокументирован
и воспроизводим как рабочий пример self-correcting RAG с реальным условным
циклом, дедупликацией контекста и измеренной стоимостью в токенах.

## MCP-сервер: search_transcripts

Поверх RAG-проекта реализован минимальный MCP-сервер (`mcp_server.py`) с одним
инструментом — `search_transcripts`. В отличие от `rag.py`/`graph_rag.py`,
сервер не генерирует ответ через LLM — он только ищет по ChromaDB (переиспользуя
`get_embed_model`/`get_collection` из `indexing.py`) и возвращает найденные
фрагменты с источниками. Генерация и рассуждение по найденному остаются на
стороне клиента — любого MCP-совместимого приложения, а не самого сервера.

**Проверено вживую:** сервер подключён к Claude Desktop через
`claude_desktop_config.json`. При вопросе, требующем поиска по интервью,
Claude Desktop самостоятельно распознал необходимость вызвать
`search_transcripts` и получил релевантные результаты с первого раза, без
дополнительной настройки.

**Почему это отдельно от `graph_rag.py`:** MCP — это протокол экспозиции
инструмента для внешних агентных систем, а не альтернативный RAG-пайплайн.
Это ортогональное дополнение: тот же поиск, что и в `rag.py`, но в
стандартизированном виде, который может вызвать любой MCP-клиент, а не
только код внутри этого проекта.
